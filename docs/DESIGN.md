# Jarvis：用可视化动作回答问题的医学内容智能体（设计方案）

> 状态：评审稿 **v0.2** · 2026-09-29（v0.1 的评审意见处理情况见第 13 节）
> 首个样例：`HOPE_案例1.pptx`（一例复发难治多发性骨髓瘤病例诊治分享，32 页）

---

## 0. 一句话目标

把一份医学 PPT 转成一个**可以被遥控的交互式网站**。用户用自然语言提问后，AI agent 不只是输出文字，而是**像播放一段微型幻灯片那样，操作网站上的真实组件**：定位、聚光、绘制图表、对比影像、逐步解说。这段演示中出现的每个数字、每句结论，都能追溯到经过审核的原文事实。

## 2. 总体架构

```
┌───────────────────────── 离线准备（可以花很长时间）─────────────────────────┐
│ PPT ─① 抽取→ raw/slides.json（每段文字、每个单元格都有精确定位）              │
│     ─② 结构化→ facts.json（事实层：原值 + 解析值 + 审核状态）                  │
│               views.json（视图层：时间轴 / 序列 / 表格 / 影像，只引用 fact id） │
│     ─③ 质量门（V1–V6，第 4 节）+ 人工审核（review 状态写回 facts.json）        │
│     ─④ 建索引 → 锚点目录、同义词表、时间索引、关系图                           │
│     ─⑤ 预编导览 → 回答计划（人工审核）→ 编译成 tour，并绑定 content_version    │
└──────────────────────────────────────────────────────────────────────────┘
                                      │ content_version = 事实层 + 视图层的哈希
┌───────────────────────────── 运行时 ──────────────────────────────────────┐
│ 浏览器：看板 ←舞台引擎（状态机 + 快照）← 步骤流   过程面板 ← 同一事件流      │
│   ▲ 提问 / 点击推荐问题                                                     │
│ Node 后端：路由 → [快速路径] 预编 tour                                      │
│                 → [慢速路径] 模型输出"回答计划" → 计划校验 → 编译器 → 步骤   │
│                    （模型经 ModelProvider 适配层调用，统一输出结构化事件）     │
└──────────────────────────────────────────────────────────────────────────┘
```

两条核心原则：

1. **agent 只输出"回答计划"，不直接输出页面或文字。** 计划由代码校验后编译成动作。数字由代码从事实层填入，差值、比例等也由代码计算。
2. **事实只保存一份。** 视图（时间轴、趋势图、表格）只引用事实 id，不复制数值。同一个值不会在不同位置出现不一致。

## 3. 内容模型

### 3.1 三层结构：通用核心 + 领域视图

| 层 | 内容 | 是否与 PPT 类型相关 |
|---|---|---|
| 动作协议 + 舞台引擎 + agent | 只认"锚点"、"事实"和"块类型" | 无关 |
| **事实层 + 通用块**（Core） | 事实（第 3.2 节）；块类型：文本段落、要点列表、表格（细到单元格）、数据序列（细到数据点）、图片 + 热点、KPI、流程、引用文献、术语表 | 无关 |
| 领域视图（Lens） | 把块和事实组织成适合这类内容的可视化和导航 | 相关 |

| Lens | 适用 PPT | 主要组件 |
|---|---|---|
| `case-course` 病程 | 病例汇报（本例） | 治疗时间轴、阶段色带、指标趋势、影像对比、分子演变 |
| `trial` 临床研究 | 研究解读（本例第 23–29 页） | 研究设计流程、基线特征表、缓解率堆叠图、K-M 曲线 + 风险人数、泳道图 |
| `review` 专题综述 | 疾病综述、专家讲座 | 主题树、证据对比矩阵、分步构建的机制示意图、推荐分级卡片 |
| `guideline` 指南 | 指南解读 | 可以点亮路径的决策流程图、推荐等级表、新旧版本对比 |
| `generic` 兜底 | 任何 PPT | 按原幻灯片顺序排列的块 + 自动生成的目录 |

遇到新的 PPT 类型，只需要新增一个 Lens，不需要新框架。

### 3.2 事实层（Fact）

**事实**是最小的可信单元：一个检测值、一个日期、一个诊断结论，或者原文中的一句陈述。

```json
{
  "id": "f.mprotein.2024-05-08",
  "loc": { "slide": 10, "shape": 18, "para": 0, "span": [4, 14] },
  "raw": "10.6412g/L",
  "parsed": {
    "kind": "exact",
    "value": 10.6412, "unit": "g/L",
    "analyte": "M蛋白", "method": "SPEP", "specimen": "血清",
    "date": { "value": "2024-05-08", "precision": "day", "basis": "stated" }
  },
  "review": { "status": "unreviewed", "proposed": null, "basis": null, "by": null, "at": null },
  "emphasis": true
}
```

**值的类型 `kind`**（第 3.4 节的图表规则和第 6.2 节的计算规则都依赖它）：

| kind | 含义 | 例子 | 能否参与计算 |
|---|---|---|---|
| `exact` | 精确测量值 | 10.6412 g/L | 可以 |
| `bound` | 只有上界或下界（`comparator`: `<` `≤` `>` `≥`） | κ <5.8 mg/L；M蛋白 <0.1% | 不能计算差值和比例；可以用于"低于/高于某阈值"的判断 |
| `not_detected` | 阴性 / 未检出，可以附检测下限 `lod` | NGS-MRD 阴性；NGF <2.8×10⁻⁵ | 不能计算；只能说"转阴" |
| `qualitative` | 定性结果 | IgG-λ型；CD138(+)；"未伴葡萄糖代谢增高" | 只能做相等或不等判断 |
| `missing` | 原文缺值 | 第 5 页 WBC 为空 | 不能使用，显示为"原文缺值" |
| `statement` | 原文中的一句陈述或结论 | 第 21 页的病例总结条目 | 只能原样引用 |

**兼容键**：`analyte`、`method`、`unit`、`specimen`/`site`、`tracer`。只有兼容键全部相同的两个事实，才能放在一起比较、计算变化，或者画在同一条曲线上。例如：
- 糖代谢 PET 与 CXCR4 显像的 SUVmax（`tracer` 不同）→ 禁止比较，只能分开展示；
- NGS-MRD 与 NGF-MRD（`method` 不同）→ 画成两条序列，不能互相计算；
- 血清游离轻链 κ（mg/L）与第 19 页没有单位的"体液免疫 κ 163.00" → `unit` 不一致或缺失，不能放进同一条序列。

**日期的依据 `basis`**：`stated`（原文写明）、`from_image`（从图片读出，比如影像上的时间戳）、`inferred`（推断得出，必须写明推断依据）。`inferred` 日期可以用于排序和绘图，但**回答中只能说"约""推断"，不能当作确定日期说出来**。

### 3.2.1 实现要点（P1.5）

- **原文单元（unit）**：PPT 中每一段文字、每个表格单元格、原生图表的每个数据点，都自动生成一个 `unit` 事实（`u.<页>.<图形>.p<段>` / `.r<行>c<列>` / `.s<序列>v<点>`），`raw` 即完整原文。人工编写的事实（`facts.src.yaml`）用 `in: <unit>` + `raw: <子串>` 指向单元内部，构建时自动计算 `span` 和前文 `ctx`。
- **解析值由代码从 `raw` 推导**，不由人工填写；V3 会独立重新解析，并与存储的值比对。
- **标签绑定（V3）**：对主要指标（M蛋白、κ、λ、κ/λ、Hb、WBC、PLT、CRP、SUVmax、FISH 各项、IHC 各项），以及检测方法（NGF / NGS）和基因名，检查数值前"最近的标签"是否与事实声明的一致（表格单元格会连同本行的行标题一起检查），可以拦截 κ↔λ、NGF↔NGS 这类错配。**局限**：部位（site）等属性目前还没有绑定检查。
- **单位推定 `implied_unit`**：只在原文同一处已经写明时使用（例如 "κ 7.07 / λ 15.1 mg/L" 共用单位）；跨页推定的单位必须走 `review.proposed`，确认后才生效。
- **V2 的规则**：每个未排除的原文单元都必须被某个视图展示；被引用的日期事实会以"日期标签"的形式展示它所在的整个单元。排除项（目录页、图上叠加的坐标刻度、致谢页）都要写明理由。
- **V4 的日期规则**：事件引用的事实，日期必须与事件日期相差不超过 7 天（按天精度）或同月（按月精度）；排序按日期区间比较；如果冲突是由待审项引起的，只报警告。
- **图片来源的数据和推断值**在构建时自动生成审核项。

### 3.3 审核状态：人工校对要成为机器能执行的准入条件

| `review.status` | 运行时的用法 |
|---|---|
| `unreviewed` | 可以使用 `raw` 的解析结果；如果有 `proposed`，**只能以"原文为 X，疑为 Y（未确认）"的形式展示** |
| `confirmed` | 原值被确认无误；如果有 `proposed`，则以 `proposed` 作为正式值，并保留原文，界面上显示"已校对"标记和修改依据 |
| `rejected` | 修正建议被驳回，使用 `raw` |
| `excluded` | 该事实不可用（例如缺值），不参与回答 |

- `review.md` 由 `facts.json` **自动生成**，不再单独手写；审核结果通过脚本或小型审核页面写回 `facts.json`（记录审核人、时间、依据）。
- **P1 遗留问题**：v0.1 的 `case.json` 在审核之前就把一些修正写进了正式字段（CRS 日期写成 2024-05-23 且精度标为 day；基因名 NARS 改成了 NRAS）。P1.5 已经处理：这两项恢复为原文，修正改为 `proposed` + `unreviewed`（`d.crs`、`f.gene.nars`）；`case.json` 已删除，由 `facts.json` + `views.json` 取代。

### 3.4 图表与展示规则

| 情况 | 显示方式 |
|---|---|
| 对数坐标上出现 `not_detected` | 不画成 0。画在坐标下方的"未检出"带上（有检测下限时，显示在检测下限的位置），用空心标记，并标注"未检出" |
| `bound` | 画在界值处，用箭头标记表示"<"或">"；数值标签保留比较符 |
| `inferred` 日期 | 数据点用虚线框标记，悬停时显示推断依据 |
| `missing` | 表格中显示"原文缺值"，图表中断开 |
| 兼容键不同 | 分开画（不同序列或分面），不能共用一条线 |
| 从图片读出的值 | 带"图读"标记；未审核前默认显示原图，数字化的版本仅作辅助 |
| 已校对的修正值 | 显示修正后的值和"已校对"标记，悬停时显示原文和修改依据 |

## 4. 离线流水线与质量门

### 4.1 流水线

| 步骤 | 脚本 | 产出 |
|---|---|---|
| ① 抽取 | `pipeline/extract.py` ✅ | 每页每个图形的文字、表格、图表数据、图片和坐标；保留上下标和标红强调；能读取 `mc:AlternateContent` 中的表格；影像红圈换算为图片坐标中的热点；每页渲染成 PNG。**待增强**：每个 run 的字符偏移，供 `loc.span` 使用 |
| ② 结构化 | `pipeline/structure.py`（调用模型，输入 raw JSON + 页面截图） | `facts.json` + `views.json` |
| ③ 质量门 | `pipeline/validate.py` | 见 4.2 |
| ③' 审核 | `pipeline/review.py` | 由 facts 生成 `review.md`；审核结果写回 facts |
| ④ 索引 | `pipeline/build_index.py` | 见第 5 节 |
| ⑤ 预编导览 | `pipeline/compile_tours.py` | 人工审核过的回答计划 → tour（第 6 节） |

### 4.2 质量门（V1–V6）

v0.1 的校验器只检查"PPT 中的数字是否在 JSON 的某个位置出现过"。这只能说明**没有遗漏**，不能说明**数据正确**：同一个值在多个位置重复存储，一处写错会被另一处掩盖；阴阳性、页码这类错误也完全查不出来。因此拆成六道门：

| 门 | 检查内容 | 能发现的错误 |
|---|---|---|
| **V1 结构** | id 唯一、schema 合法、引用的 id 都存在、页码在范围内 | 悬空引用、字段缺失 |
| **V2 遗漏检查** | PPT 文字中的每一个数字和日期，都必须被某个事实的 `loc` 覆盖（按位置判断，不按"出现过"判断） | 漏抽的内容 |
| **V3 事实回读** | 按 `loc` 回到 `raw/slides.json` 取出原文片段，重新解析，再与 `raw`、`parsed` 的值、单位、比较符、日期、阴阳性逐项比对 | 数值被改、单位错、`<` 丢失、阴性写成阳性、页码或位置错 |
| **V4 视图一致性** | 视图层只允许引用 fact id（出现字面数值即报错）；同一条序列里的事实，兼容键必须一致；时间轴事件的日期必须等于它所引用事实的日期 | 跨视图不一致、混画不兼容的数据 |
| **V5 审核准入** | `proposed` 只有在 `confirmed` 后才会进入正式值；`inferred` 日期必须写明依据；图读数值必须标记来源 | 未经审核的修正被当作事实 |
| **V6 版本** | 计算 `content_version`；所有预编 tour 必须绑定当前版本，否则标记为失效 | 数据修改后仍在播放旧答案 |

**变异回归测试**（`tests/test_validate_mutations.py`）：自动对事实做篡改，每一种篡改都必须被某道门拦下，否则测试失败。至少包括评审中实测的三类：
- 把数值改掉（10.6412 → 999）→ V3；
- 把阴性改成阳性 → V3；
- 把来源页改成另一个合法但错误的页码 → V3；

以及：丢掉比较符（<5.8 → 5.8）、改单位、把某个日期改为另一天、在视图中写入字面数值、把兼容键不同的事实放进同一条序列、未确认就启用 `proposed`、修改数据后不更新 tour 的版本。

## 5. 索引：怎样让 agent 定位得既准又快

### 5.1 锚点目录

页面上每个可以被指向的东西都有唯一 id，同时是 DOM 锚点（`data-anchor`）。粒度分四级：`section` → `block`（一张图 / 一张表）→ `item`（一行 / 一个事件）→ `value`（一个数据点 / 一个单元格 / 一个热点）。**value 级锚点和事实一一对应。**

锚点目录中的每条记录包括：id、类型、可读文本、上级、所属章节、日期和治疗阶段、实体、关联锚点、**可用动作**、**绑定的 fact id 和它的审核状态 / kind / 兼容键**。模型从目录中就能看出哪些值可以计算、哪些只能展示、哪些还没有审核。

### 5.2 辅助索引

| 索引 | 作用 |
|---|---|
| 实体 / 同义词表 | 把用户的说法映射到锚点（埃纳妥 = 埃纳妥单抗 = elranatamab）。模型补充的同义词只用于检索，不作为回答内容 |
| 时间索引 | 日期 → 事件、事实、影像；治疗阶段 → 时间区间。`inferred` 的日期参与检索，但带标记 |
| 关系图 | 事件 → 相关的表格、影像、事实 |

### 5.3 运行时检索

- 单个病例：锚点目录大约 2–3 万 token，整份放进系统提示词（API 模式下开启 prompt caching），由模型直接选择锚点和事实。
- 内容很多时：先做混合检索（BM25 + 向量 + 实体 + 时间过滤），取 top-k 块及其上下级，再交给模型。

### 5.4 评测

`eval/questions.jsonl`：每道题标注必须命中的事实和锚点、禁止出现的内容、期望的拒答行为。统计：事实命中率和精确率、**计划校验被拒率**、首个动作延迟、PPT 外问题的拒答正确率。

## 6. 回答：计划 → 编译 → 舞台

### 6.1 为什么要先出计划

只检查"引用的锚点存在"，拦不住"引用了真实的锚点，却说错了事实"。所以模型不直接写解说词，而是先输出一份**回答计划**；由代码校验这份计划，再编译成动作和文字。

### 6.2 回答计划（Answer Plan）

```json
{
  "answer_id": "a_7f3c",
  "question": "患者有哪些高危因素？髓外病灶出现在哪些部位？",
  "claims": [
    { "id": "c1", "type": "quote",
      "facts": ["f.sum.case.f2"],
      "uncertainty": "none" },
    { "id": "c2", "type": "change",
      "facts": ["f.fish.1q21.2023-06", "f.fish.1q21.2026-01"],
      "derivation": { "op": "compare", "inputs": ["f.fish.1q21.2023-06", "f.fish.1q21.2026-01"] },
      "template": "1q21 扩增：{{f.fish.1q21.2023-06}}（初诊）→ {{f.fish.1q21.2026-01}}（2026.01）" },
    { "id": "c3", "type": "list",
      "facts": ["f.emd1.site", "f.emd2.site.breast", "f.emd2.site.iliac", "f.emd3.site"],
      "template": "髓外病灶：{{f.emd1.site}} → {{f.emd2.site.breast}}、{{f.emd2.site.iliac}} → {{f.emd3.site}}" }
  ],
  "not_in_source": [],
  "visual_intent": [
    { "claim": "c2", "show": "morph", "target": "mol.fish.1q21" },
    { "claim": "c3", "show": "sequence", "targets": ["img.emd1_ct.h1", "img.emd2_breast.h1", "img.emd2_iliac.h1", "img.emd3_groin.h1"] },
    { "claim": "c1", "show": "spotlight", "target": "sum.case.f2" }
  ]
}
```

**claim 的类型和对应规则**

| type | 含义 | 规则 |
|---|---|---|
| `value` | 陈述一个值 | 数字只能通过 `{{fact}}` 占位符填入，由代码按 kind 格式化（保留比较符、单位、"未检出"字样） |
| `change` / `ratio` | 变化或比例 | 由代码计算；输入必须都是 `exact` 且兼容键一致，否则拒绝（`bound` / `not_detected` 只能说"降至界值以下 / 转阴"） |
| `list` / `sequence` | 列举或排序 | 只能组合占位符；排序依据是事实的日期（inferred 日期会自动加上"约"） |
| `quote` | 引用原文陈述，包括解释性、因果性的结论 | 只能引用 `kind=statement` 且审核状态允许的事实，**逐字显示**。这是因果结论唯一的来源 |
| `not_in_source` | PPT 中没有答案 | 必须给出 `nearest`（最接近的锚点），舞台会展示这些内容并说明"本病例资料未涉及" |

**模板中的自由文字**只允许连接性的短语，由校验器检查：
- 不能出现任何数字（数字必须来自占位符）；
- 不能出现 claim 所引用事实之外的医学实体（按同义词表检查）；
- 不能出现因果或解释性用语（"因为""导致""提示""说明"等），这类内容只能用 `quote`。

`callout(anchor, text)` 的标注文字和 `say` 使用**同一套约束**（text 必须是一个编译过的 claim），不能附带任意文字。

**剩余风险**：自由文字即使经过限制，仍可能用词不当（比如"明显下降"）。对策是尽量不用自由文字，常用句式做成固定模板；另外可以选配一道"复核"步骤，由模型判断编译后的文字是否被所引事实支持（会增加延迟，默认只在评测时启用）。

### 6.3 编译器

计划 → 校验（第 6.2 节的规则 + 事实的审核状态 + 兼容键）→ 生成步骤（每一步 = 镜头 + 动作 + 编译后的文字 + 引用）。任何一个 claim 被拒绝，都会以结构化错误反馈给模型重试一次（最多 1 次）；仍失败的 claim 会被丢弃，并在过程面板中显示原因。

**流式**：模型逐个输出 claim，每个 claim 通过校验后立即编译、入队、播放，不需要等整份计划生成完。

### 6.4 舞台与聚光

- 进入舞台模式：看板变暗、轻微模糊、后退；相关组件以 FLIP 动画飞到中央（是真实组件，不是截图）；按步骤播放。
- 突出重点的方式：SVG 遮罩聚光灯（可以在多个目标之间移动）、放大、数字滚动、引线标注、对比箭头（变化幅度由编译器计算）、PPT 原文标红的内容带微光提示。
- 组件自带的动画原语：时间轴扫描、阶段依次点亮；折线逐段绘制、坐标变换；表格行闪烁、单元格放大；影像热点描边、前后滑块对比；VAF 条形变形；堆叠柱生长、K-M 曲线揭开；分步构建的机制图。

### 6.7 Agent 过程面板

默认展开，可以折叠。它与舞台共用同一个事件流（第 7 节），逐行显示，每行带时间戳和耗时：

1. **路由**：是否命中预编 tour，是哪一个，版本是否有效；
2. **检索**：用到的锚点和事实（可以点击定位）；
3. **回答计划**：每个 claim 的类型、所依据的事实、推导方式、不确定性；
4. **校验**：每个 claim 通过或被拒，以及原因（例如"不兼容比较：CXCR4 与糖代谢 PET"、"引用了未确认的修正值"、"模板中出现了数字"），重试情况；
5. **执行**：每一步的 `step_id` 及其状态（排队 / 播放中 / 完成 / 取消 / 丢弃）；
6. **指标**：首个动作延迟、总耗时、token 用量和缓存命中情况（如果提供方返回了这些数据）。

显示原则：只显示结构化计划，以及提供方实际返回的思考摘要，不编造推理过程。每条记录都可以展开看原始 JSON；整次回答可以导出为 trace 文件，用于回放和提交问题报告。对外演示时隐藏系统提示词和本机路径。

## 7. 舞台状态模型：暂停、回退、打断

**标识**：每次回答有 `answer_id`（服务端生成）；每一步有 `step_id` 和 `seq`（从 0 开始递增）；每个事件都带 `content_version`。

**客户端状态机**

```
idle → planning → playing ⇄ paused → done
          │          │
          └──────────┴──(新问题 / 用户取消)──→ cancelled
```

| 机制 | 规则 |
|---|---|
| **打断** | 用户发出新问题时，客户端先把当前 `answer_id` 标为 cancelled，并通知服务端取消；服务端中止模型调用（结束子进程或断开请求）。**之后到达的、属于旧 `answer_id` 的事件一律丢弃**，只在过程面板中记为"已丢弃" |
| **去重** | 按 `(answer_id, seq)` 去重；乱序到达的步骤先缓存，按 `seq` 顺序执行 |
| **幂等** | 动作的定义是"把舞台设置到目标状态"，而不是"在当前状态上叠加"。重复执行同一步，结果相同 |
| **快照** | 每一步开始执行前，保存一份舞台状态快照（镜头、聚光目标、图表范围和坐标、打开的影像、时间轴游标） |
| **上一步** | 恢复到第 n−1 步的快照，再用正常的进场动画重新播放第 n−1 步。**不做倒放** |
| **暂停** | 冻结 GSAP 时间线和后续队列；已经到达的步骤继续缓存 |
| **倍速 / 跳过** | 调整时间线的速度；跳过 = 直接应用下一步的目标状态 |
| **版本** | 事件中的 `content_version` 与页面当前加载的版本不一致时，拒绝执行，并提示刷新 |

## 8. Agent 运行时与模型提供方

| 路径 | 条件 | 做法 | 目标延迟 |
|---|---|---|---|
| 快速路径 | 点击推荐问题，或提问匹配到预编 tour，并且版本有效 | 直接播放 | < 0.5 s |
| 慢速路径 | 没有命中 | 模型流式输出计划 → 按 claim 校验、编译、播放 | 首个动作 1–3 s（取决于提供方） |
| 追问 | "放大一点""换成对数坐标" | 在当前快照上做增量操作 | < 1 s |

### 8.1 统一接口

```ts
interface ModelProvider {
  plan(req: { answerId: string; question: string; context: CatalogRef; schema: JSONSchema },
       signal: AbortSignal): AsyncIterable<ProviderEvent>;
}
type ProviderEvent =
  | { type: "claim"; claim: Claim }          // 一个完整的 claim（已通过 JSON 解析）
  | { type: "thinking_summary"; text: string } // 只在提供方返回时出现
  | { type: "usage"; inputTokens: number; outputTokens: number; cacheRead?: number }
  | { type: "error"; code: "timeout" | "parse" | "provider" | "cancelled"; detail: string }
  | { type: "done" };
```

所有提供方都必须通过**同一组契约测试**：正常输出、JSON 截断、非法 claim、超时、取消。业务层（校验器、编译器、舞台）只依赖这个接口。

### 8.2 `claude-code` 提供方（内部演示阶段，使用本人订阅）

- `claude -p --output-format stream-json` 输出的是 **CLI 事件流**（系统消息、助手消息、结果等），不是业务动作流。适配器负责：逐行解析 NDJSON → 从助手消息中取出结构化输出 → 增量解析出完整的 claim → 按 schema 校验 → 转换成 `ProviderEvent`。
- 流式增量输出需要加 `--verbose --include-partial-messages`；结构化输出用 `--json-schema`。
- **隔离本机环境**（这些参数已在 macmini-4 上用 Claude Code 2.1.220 的 `--help` 核对过）：
  - 注意：`--bare` 可以一次性跳过 hooks、插件、CLAUDE.md 等，但它**只接受 API Key 认证，不读取订阅登录**，所以订阅模式下不能用；
  - 改为逐项关闭：`--tools ""`（禁用所有工具）、`--strict-mcp-config`（不加 `--mcp-config`，即不加载任何 MCP）、`--setting-sources` 限定只读取必要的配置来源、在专用的空目录中运行（不会读到 CLAUDE.md）、`--no-session-persistence`、`--system-prompt` 替换默认系统提示词；
  - 这些组合在 P3 **逐项实测**：确认工具确实不可用、MCP 没有加载、没有读到 CLAUDE.md、没有写入会话文件。
- **超时和取消**：首个事件 20 s 内未到达，或整体超过 90 s，就结束子进程（先 SIGTERM，再 SIGKILL）；`AbortSignal` 触发时同样处理。
- **并发**：同一时间只运行 1 个子进程（新问题会取消旧问题）。
- **使用范围**：仅限本人操作的内部演示；公开链接必须设置访问码，他人只能观看，不能自行提问。

### 8.3 `anthropic-api` 提供方（对外阶段）

使用 Console API Key；原生流式输出，开启 prompt caching；支持多人并发。通过同一组契约测试后，只需要改一个配置项就能切换。

## 9. 视觉设计：浅色、专业、酷

- 底色：极浅的蓝灰（约 `#F6F8FB`）加很淡的点阵或网格；卡片为白色，用轻微阴影和 1px 描边
- 主色：深海军蓝（延续原 PPT 和医院 VI）；强调色为青蓝/电光青（聚光和高亮）；语义色：缓解用青绿，进展用珊瑚红，治疗阶段用一组低饱和色带
- "酷"主要来自动效：聚光灯遮罩、FLIP 飞入、折线描绘、数字滚动、热点描边、时间轴扫描、玻璃质感舞台层

- 可访问性：遵守 `prefers-reduced-motion`；颜色之外同时用形状或标记区分含义（例如"未检出"用空心标记，"推断"用虚线框）
